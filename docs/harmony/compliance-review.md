# 命名规范与侵权风险评估

> 对象：青芒短视频（原「果鉴」）
> 日期：2026-11-06
> 性质：**工程层面的风险梳理，不构成法律意见**。涉及上架、商用、分发前，应另行做正式合规审查。

---

## 一、评估方法

1. 全量扫描源码、配置、资源、文档、脚本中的第三方品牌词（红果 / hongguo / 抖音 / 果鉴 / guoapp 等），先排除构建缓存与二进制。
2. 把命中项按 **「能不能改」** 分成四层，而不是一刀切替换——这是本次评估最关键的一点：有些字符串是**协议数据**，改了功能立即失效；有些是**磁盘文件标识**，改了会丢用户数据。
3. 对每一层给出处理结果与依据。

---

## 二、四层风险与处理

### A 层｜用户可见的商标使用 —— 已清除

| 位置 | 原值 | 现值 |
|---|---|---|
| `AppScope/.../string.json` `app_name` | 果鉴 | **青芒短视频** |
| `entry/.../string.json` `EntryAbility_label` | 果鉴 | **青芒短视频** |
| `entry/.../string.json` `EntryAbility_desc` | 红果短剧 | 短视频播放入口 |
| `entry/.../string.json` `module_desc` | 国剧主模块 | 主模块 |
| `oh-package.json5`（根）`description` | 国剧 · HarmonyOS 7 车机版（超级桌面） | 青芒短视频 · HarmonyOS 7 手机版（兼容鸿蒙智行车机超级桌面） |
| `entry/oh-package.json5` `description` | 国剧车机版主模块 | 青芒短视频主模块（EntryAbility） |
| `pages/Index.ets` 顶部小标题 | 果鉴 | 青芒短视频 |
| `pages/Index.ets` 宽屏侧栏 | 果鉴（2 字） | 青芒 / 短视频（两行副标，避免 96vp 窄栏溢出） |
| `README.md` 项目描述 | 含第三方平台名 | 中性表述「上游开源实现」「内容源」 |
| 桌面图标 | 红底白播放三角，配色接近第三方品牌色 | 全新青→黄绿渐变 + 几何层叠（见 `docs/icon/`） |

> 桌面图标是这次最该换的一处：原来的红色渐变 + 白播放键，在视觉上会与已有短视频产品产生联想。新图标用「青芒」自身的青绿意象 + 用户偏好的莱姆绿，独立且可识别。

### B 层｜代码内部命名与注释 —— 已中性化

| 原命名 | 新命名 |
|---|---|
| `net/HongguoApi.ets` / `class HongguoApi` | `net/ContentApi.ets` / `class ContentApi` |
| `hongguoArgus()` / `hongguoLadon()` | `buildArgus()` / `buildLadon()` |
| 日志 TAG `GuoAppCar / Entry / Material / Layout` | `QingMangCar / Entry / Material / Layout` |
| XComponent id `guoapp_video` | `qingmang_video` |
| 注释里的「红果接口 / 红果 CDN / 红果的弹幕」等 21 处 | 「内容源 / 上游服务」 |
| `EntryAbility.ets` 窗口方向注释里的「酷狗 / 哔哩 / 内容源满屏」 | 「横屏类应用能满屏」（复核时补漏，不再点名第三方产品） |
| 注释里对上游 Go 文件名的具体路径引用 | 「上游签名实现 / 上游媒体解密实现」 |

**命名规范结论**：改为「内容源 / 上游服务」后，**除 C 层明确列出的协议必需字段外**，源码、资源、配置、脚本中不再出现第三方商标词；模型、网络、视图分层清晰；`DanmakuComment.offsetMs` 这类带单位的字段名是规范做法。遗留的口语化注释（「糊一屏」等）不影响功能，若要对外开源再统一为书面语。

> **复核记录（2026-11-06，收尾轮）**：对 `entry/src`、`AppScope`、两个 `oh-package.json5` 重新做了一次全量词表扫描，发现首轮漏掉 3 处（两个模块描述 + 一处注释），已全部修掉。剩余命中仅 4 项，全部是下面 C 层的刻意保留值：`display_name`、`Prefs.STORE_NAME`、`bundleName`、根包 `name`。这说明「扫一遍就宣布清零」不可靠，保留项必须逐条过一遍。

### C 层｜协议必需，改了就坏 —— 明确保留，并加了防误改注释

| 保留项 | 为什么不能改 |
|---|---|
| `ContentApi.ets` 的 `APP_BASE` / `REGISTER_URL` / `USER_AGENT` | 请求签名与风控校验逐字依赖这些值，改一个字符就返回空 body |
| `display_name: '红果免费短剧'`（设备注册参数） | 服务端按此值识别客户端类型，是**上行协议字段**，不是界面文案 |
| 各接口路径、风控头名 `X-Gorgon / X-Argus / X-Ladon` | 协议本身 |
| `Prefs.STORE_NAME = 'guoapp_store'` | 这是**磁盘偏好库文件名**。改名 = 新建一个空库，用户的主题、倍速、弹幕设置、播放历史全部丢失。已加注释说明 |
| `bundleName: com.dudu.guoapp.car` | 包名不是用户可见名称。改动会导致：装包变成「另一个应用」、无法覆盖升级、已存数据丢失、车机侧若按包名做白名单会全部失效。**收益为零、代价明确**，因此保留 |
| `scripts/build.sh` 的 `guoapp.p12` / `keyAlias "guoapp"` | 本地签名证书文件名与别名，与证书内容绑定，改了签名失败 |
| `oh-package.json5`（根）`name: "guoapp-harmony"` | 内部包标识，与工程目录名、hvigor 构建缓存键绑定，不是用户可见名称；改名收益为零且可能打断增量构建 |
| `README.md` 的上游 GitHub 链接 | 开源来源署名，保留反而是合规要求 |

> 这些项已在源码里加了「兼容性常量 / 磁盘文件标识 / 证书绑定」注释（`ContentApi.ets` 文件头 + `display_name` 行内、`Prefs.ets`、`app.json5`、`build.sh`），防止以后有人按「敏感词清理」再误删一次。根 `oh-package.json5` 的 `name` 不便写注释（ohpm 解析器兼容性），仅在本文档备案。

### D 层｜实质性合规风险 —— **改命名解决不了，必须如实说明**

前三层都是「标识」。这一层是这个应用**本身的运行方式**，本轮没有改，也不能靠改代码解决：

| # | 风险 | 说明 |
|---|---|---|
| 1 | **内容来源与版权** | 应用聚合、播放第三方平台享有权利的影视内容，未见授权链路。界面上加「版权归原作者所有」的声明**不等于取得授权**，只降低误导性，不消除风险 |
| 2 | **接口访问方式** | 通过复刻私有风控签名头（X-Gorgon / X-Argus / X-Ladon / SM3 摘要）访问上游接口，实质上在模拟官方客户端。这类行为可能触及服务条款，甚至被认定为规避技术措施 |
| 3 | **上游开源实现与许可证** | README 声明原项目以 **GPL-3.0** 发布、本项目同样遵循。GPL-3.0 是强著佐权许可：**一旦对外分发二进制，就负有提供对应完整源码的义务**。签名与 CENC 解密算法逐字节对齐上游实现，因此当前工程整体应按 GPL-3.0 处理，「个人私下使用」不触发分发义务，但公开提供安装包会触发 |
| 4 | **分发与上架** | 以上三点决定：这个包适合**个人学习研究**，不适合公开分发或商业上架。README 与「我的」页已按这个定位写明 |

**明确结论**：本次做的是「去商标化 + 命名规范化」，它消除了**冒用他人品牌标识**这一类风险；上表 D 层的风险**一条都没有被消除**。如果目标是公开分发或上架，需要的是更换为有明确授权的内容源 / 官方开放 API，而不是继续在命名上做文章——那已经超出「改代码」的范围。

## 三、顺带做的安全加固

| 项 | 处理 |
|---|---|
| 构建脚本硬编码签名口令 | 改为 `GUOAPP_KEY_PWD` 环境变量优先，保留兼容默认值以免打断本机流程；正式构建应显式设置 |
| 唯一一个明文 HTTP 常量 | 确认是**未被引用**的死常量，已删除。因此**不**新增 `network_config.json` 放行明文（开了反而是安全降级） |
| 「我的」页免责声明 | 从一句笼统的「内容来源于网络第三方接口」改为明确版权归属 + 不上传/不存储/不二次分发 + 仅限个人学习研究 |

---

## 四、待办（未做，列出来避免遗漏）

1. 若将来要正式分发：更换有授权的内容源，并删除私有签名复刻相关模块。
2. 按 GPL-3.0 补齐 `LICENSE` 文件、版权头与完整源码获取方式；分发安装包时同步提供对应源码，不要只在 README 里写一句协议名。
3. 应用内补充「内容来源说明」页面，把版权归属与用户权利义务写清楚（当前只在「我的」页底部一行）。
4. 若确需更换 `bundleName`：应在尚无真实用户时一次性完成，并同步改 `Prefs.STORE_NAME`、车机白名单、验证脚本里的 `BUNDLE`，然后做一次完整的数据迁移验证。
